# AccessEdu — платформа оценки и повышения веб-доступности образовательных ресурсов

Платформа проверяет страницы курсов, учебные материалы и порталы по WCAG 2.2, ставит оценку от 0 до 100,
объясняет каждое нарушение на русском или английском, строит план исправлений («что исправить первым и на сколько
вырастет оценка») и хранит историю, чтобы видеть прогресс.

* **Бэкенд:** Python 3.11+, Flask, Pydantic v2, SQLite, BeautifulSoup.
* **Фронтенд:** React 19, сборка esbuild, без тяжёлых зависимостей.

## Быстрый старт

```bash
make install   # pip install + npm install
make run       # собрать фронтенд и запустить всё на http://localhost:8000
```

Без `make`:

```bash
cd frontend && npm install && npm run build
cd ../backend && pip install -r requirements.txt && python run.py
```

Откройте http://localhost:8000. На пустом обзоре нажмите **«Загрузить демо-данные»**: появятся три учебные страницы
с историей проверок, динамикой и статусами замечаний.

Режим разработки (пересборка фронтенда при изменениях, прокси `/api` на бэкенд):

```bash
make dev        # бэкенд :8000, интерфейс http://localhost:5173
```

Docker: `docker compose up --build` → http://localhost:8000 (данные хранятся в томе `accessedu-data`).

Тесты: `make test` (105 тестов: правила, CSS-контраст, оценка, API, защита от SSRF, инструменты, аудит, обход сайта, планировщик, обучение).

## Как оценивается доступность

* В оценку входят только **применимые автоматические** правила: если на странице нет видео, правила про субтитры ничего не меняют.
* Вес правила зависит от серьёзности: критично 10, серьёзно 7, умеренно 3, незначительно 1.
* Правило без нарушений даёт полный балл; с нарушениями — частичный (не больше 50 %) и тем меньший, чем больше доля нарушивших элементов.
  Так оценка растёт по мере исправления, но страница с критической ошибкой не получит «почти 100».
* Пункты «проверить вручную» (аудио без расшифровки, текст на фоновой картинке и т. п.) в оценку не входят — они показываются отдельно.
* Уровень WCAG («A», «AA») присваивается, если по этому уровню нет нарушений. **Автоматическая проверка покрывает лишь часть критериев**, поэтому
  результат нужно дополнять ручной проверкой с клавиатурой и скринридером — об этом сказано и в интерфейсе.

Код: `backend/app/a11y/scoring.py` (формулы, ≈70 строк).

Слои зависят только «вниз»: `api → services → repositories → db`; `a11y` не знает ни о Flask, ни о SQLite, поэтому
движок можно использовать отдельно (CLI, CI, другой фреймворк): `from app.a11y.analyzer import analyze`.

## Как расширять

### Добавить правило проверки

1. Создайте функцию в любом модуле `backend/app/a11y/rules/` (или новый модуль, подключите его в `rules/__init__.py`):

   ```python
   @rule(
       id="table-caption", wcag=["1.3.1"], level="BP", impact="minor", principle="perceivable",
       tags=["tables"],
       bad="<table><tr><th>A</th></tr></table>",
       good="<table><caption>Оценки</caption><tr><th>A</th></tr></table>",
   )
   def table_caption(doc: Document, report: RuleReport) -> None:
       for table in doc.find_all("table"):
           report.checked()              # правило применимо к этому элементу
           if not table.find("caption"):
               report.fail(table)        # или report.review(table) — «проверьте вручную»
   ```

2. Добавьте тексты в `locales/ru.json` и `locales/en.json`: `{"title": …, "message": …, "fix": …}`
   (в `message` можно использовать `{поля}` из `report.fail(el, data={...})`).
3. Запустите `make test`. Тесты сами проверят, что правило находит свой «плохой» пример, пропускает «хороший» и имеет тексты на всех языках.

Новый критерий WCAG добавляется в `a11y/wcag.py`. Оценка, отчёты, фильтры, страница «Правила» и план исправлений подхватят правило автоматически.

### Добавить язык

* Правила: `backend/app/a11y/locales/kk.json` (по образцу `en.json`; недостающее берётся из английского).
* Интерфейс: `frontend/src/i18n/kk.js` (по образцу `en.js`), затем строка в `i18n/index.jsx` (`DICTS`, `LANGUAGES`) и в `prefs.jsx`.
* Для казахского формы множественного числа такие же, как в английском: `{ one, other }`.

### Добавить пункт ручного аудита или урок

* Пункт аудита: кортеж `Item(...)` в `backend/app/a11y/checklist.py` (принцип, критерии WCAG, тексты ru/en).
* Урок: словарь в `backend/app/data/academy.py` (тексты ru/en, вопросы; правильный ответ хранится один раз и клиенту не отдаётся). Тест `test_workflow` проверит согласованность переводов.
* Событие уведомления: правила в `services/notifications.py`, текст — ключ `event.<тип>` в словарях интерфейса.

### Изменить схему БД

Добавьте файл `backend/app/db/migrations/002_название.sql` — он применится один раз при старте. Существующие миграции не правьте.

### Добавить страницу или эндпоинт

* API: модуль в `backend/app/api/` с `Blueprint`, регистрация в `factory.py`. Запросы валидируйте схемой из `schemas/requests.py`, ошибки бросайте через `ApiError`.
* Интерфейс: страница в `frontend/src/pages/`, маршрут и пункт меню в `app.jsx`, тексты в оба словаря.

## Безопасность

* **SSRF.** Загрузчик (`services/fetcher.py`) пропускает только http/https, запрещает логин/пароль в адресе, проверяет IP **в момент соединения**
  (защита от DNS-rebinding) и после каждого перенаправления, ограничивает размер, время и число редиректов; по умолчанию внутренние сети
  (localhost, 10.x, 192.168.x, 169.254.x и т. д.) закрыты. Для интранета включите `ACCESSEDU_ALLOW_PRIVATE_HOSTS`.
* Отчёты: HTML экранируется, CSV защищён от формульных инъекций (`=`, `+`, `-`, `@`).
* Входные данные строго валидируются (лишние поля отклоняются), SQL — только параметризованный.

> В платформе нет авторизации пользователей: она рассчитана на работу внутри организации. Если её нужно открыть в интернет,
> поставьте перед ней обратный прокси с авторизацией или добавьте слой пользователей (удобная точка — `factory.py`, `before_request`).

## Известные ограничения и идеи развития

* Движок анализирует **HTML и CSS без выполнения JavaScript**: содержимое, которое рисуется скриптами, проверяется по исходному коду.
  Для SPA-страниц вставляйте HTML после рендера (из «Инспектора» браузера). Следующий шаг — проверка через headless-браузер (Playwright) как второй источник HTML.
* Контраст считается по встроенным и подключённым в `<style>` стилям; внешние таблицы стилей, `@media`, `opacity`, `color-mix()` не учитываются
  (в таких случаях платформа не ставит ложных нарушений).
* Проверка PDF/DOCX-материалов не реализована: такие ссылки попадают в «проверить вручную».
* Планировщик работает внутри процесса запуска (`run.py`, `wsgi.py`); при нескольких процессах gunicorn проверка не дублируется (ресурс «занимается» атомарно). Для cron можно вызвать `app.services.scheduler.run_due(settings)`.
* Обход сайта идёт по ссылкам на HTML-страницы того же хоста (глубина 1–2, до 50 страниц), без запуска JavaScript.
* Читаемость: индекс Флеша для русского (Оборнева) и английского; для других языков не рассчитывается.
* Идеи: роли и авторизация, отправка уведомлений на почту, проверка PDF/DOCX, проверка через headless-браузер, сравнение коллекций, казахский интерфейс.
